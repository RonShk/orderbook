# v2: cancels and modifies

v1's sorted vectors, plus cancel and modify by order id. The data structure is the same as v1. The point of v2
is to pin down the rules, so v3 has a reference to match.

## Rules

**Cancel** takes an id and a side.

- If the order is resting on that side, it is removed and the result is `Canceled`.
- Otherwise, the result is `NotFound`. That covers an id that was never used, an order that has already filled,
  an order already canceled, and the wrong side. The book doesn't keep a record of finished orders, so it
  can't tell these apart.
- Only what's left is removed. Trades from earlier partial fills stand.
- A cancel never trades.

**Modify** takes an id, a side, a new quantity and a new price.

- The new quantity is the **remaining** quantity, not the order's total size. An order of 10 that has filled 6
  and is modified to 8 now has 8 left.
- A quantity or price of 0 or less is `Rejected`, and the order is left as it was. There is no cancel by
  modify. Cancel is the only way to remove an order.
- If the order isn't resting on that side, the result is `NotFound`.
- The side can't change. To switch sides, cancel and add a new order.
- The order keeps its id.

Queue priority after a modify:

| Change | Place in the queue | Can it trade? |
|---|---|---|
| Same price, same quantity | Kept (nothing changes) | No |
| Same price, lower quantity | Kept | No |
| Same price, higher quantity | Back of that price level | No |
| New price | Back of the new price level | Yes, if it crosses; the rest then rests |

No modify ever moves an order forward. This is the usual rule on futures exchanges: making an order smaller
doesn't hurt anyone queued behind it, but making it bigger or repricing it does.

## Design

- Commands are read line by line: `Buy`/`Sell` lines are adds as in v1, and `Cancel` and `Modify` lines name an
  add by its id. The format is in `tests/README.md`.
- Cancel and modify find the order with a linear scan of the side they are given (`std::find_if` on the id).
- A modify that changes the price or raises the quantity erases the order and sends a copy with the new values
  through `add_order`. That gives it the normal matching, and `lower_bound` places it at the back of its price
  level.
- A modify that only lowers the quantity changes it where it is.
- Cancel and modify results are folded into the checksum along with trades, so v3 has to match the results as
  well as the trades.

## Observations

- At 1M commands, the mixed run takes about twice as long as the add-only run (1.69 s against 0.86 s), even
  though it has 30% fewer adds and so fewer resting orders. A cancel or modify scans one whole side whenever
  the id isn't there, and most of them in this workload aren't. That is likely where the extra time goes, but
  it hasn't been profiled: `perf` needs `kernel.perf_event_paranoid` lowered on this machine.
- About 78% of cancels and modifies come back `NotFound`. About 77% of adds trade as soon as they arrive, so most
  targets have already filled, even when the generator only picks from the latest adds. Real markets cancel
  resting orders far more often. To make most cancels hit, the generator would need to simulate the book.

## What v3 targets

Price-indexed levels with a linked list per level, a memory pool, and a map from id to the order's node. Insert,
cancel and the in-place part of modify become O(1), and a missed lookup costs one hash probe instead of a scan.
